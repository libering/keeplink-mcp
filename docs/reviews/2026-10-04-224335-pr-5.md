# retry_task tool + multi-format archive_and_cite citations (PR #5)

PR #5 delivers improvements C (manual retry of permanently failed tasks) and H (multi-format citations), plus the `archive_and_cite` foundation, across the repository, API, and MCP layers of KeepLink-MCP. The retry path is a status-guarded `failed -> pending` UPDATE exposed through a new `POST /api/retry` endpoint and `retry_task` MCP tool; citations are produced by a new pure-function builder (`citation/builder.py`) that renders four formats in two states (complete/pending), surfaced through `POST /api/cite` and the `archive_and_cite` tool. No DB schema change; the new write reuses existing columns and the new read path reuses `validate_url` / `find_recent_task` / `create_task`. The design holds to the stated philosophy — the builder does zero I/O, and both new paths fail fast on bad input rather than falling back silently.

Watch for: (1) the cache-hit `archived_at` is sourced from `ArchiveTask.updated_at`, which is a last-mutation timestamp, not a dedicated "archived at" time — **confirmed**, a semantic approximation worth noting; (2) the `retry_task` None-vs-RetryRejected discrimination has a benign TOCTOU window that can only ever downgrade a 404 to a 409, never corrupt state — **confirmed**; (3) `archive_and_cite` pending guidance reads `data['task_id']` with a hard key access that assumes a well-formed 200 body — **confirmed**, low risk but inconsistent with the defensive `.get()` used for errors.

**Verdict**: APPROVED

## High-level view

The retry transition is atomic where it matters. The repository issues a single `UPDATE ... WHERE task_id = ? AND status = 'failed'` and keys its decision off `rowcount`, so a concurrent worker transition can never cause a non-failed task to be mutated. The only follow-up read is to tell "not found" (404) from "found but not failed" (409) when `rowcount == 0`; because the guarded UPDATE already proved no mutation happened, that read is purely for error classification and the worst case is a 404 reported as a 409 for a task that was deleted in the microsecond between. State integrity is never at risk.

The citation builder is a pure module — no network, no DB, no LLM, no clock read (dates come from the caller-supplied `archived_at` via `strftime`), which is exactly the deterministic, LLM-free contract the project promises. The complete/pending invariant is enforced with a single fail-fast check: `archived_url` and `archived_at` must both be set or both be None, and any half-set pair raises `ValueError` rather than being masked. Format selection is a two-table dispatch (state × format) of small single-purpose formatters, so the markdown default stays byte-for-byte identical to the previous output and new formats are additive.

The API surface is a clean three-way mapping. `/api/retry` maps `ArchiveTask | RetryRejected | None` to 200/409/404, and `/api/cite` returns a structured citation whose pending state is defined solely by a null `archived_url`. Invalid citation formats are rejected by the enum-typed `CiteRequest.format` as a 422 — fail-fast, no silent downgrade to markdown. The MCP tools proxy these verbatim and preserve the existing backend-unavailable contract.

The main semantic caveat is what "archived_at" means on a dedup cache-hit: it is `updated_at`, the row's last-write time, which equals the archive time immediately after `mark_success` but could drift if the row were ever updated again. There is no dedicated archived-at column, and adding one would be a schema change the PR deliberately avoids, so this is a documented approximation rather than a defect.

### Status-guarded retry and the classification read

`TaskRepository.retry_task` is the behavioral core of improvement C. The transition is a single statement:

```python
update(ArchiveTask)
  .where(ArchiveTask.task_id == task_id, ArchiveTask.status == TaskStatus.FAILED)
  .values(status=PENDING, retry_count=0, next_retry_at=None, error_message=None, ...)
```

The `status == FAILED` predicate is what makes the "no mutation unless failed" guarantee real: a pending, processing, or success row never matches, so no column is touched and `rowcount` is 0. This is the right primitive — it closes the race against a concurrent worker that might flip the same row from processing to success, because the database, not application code, arbitrates the guard.

The follow-up is the one place worth understanding precisely. When `rowcount == 0`, the code issues `get_task` to decide between `None` (404) and `RetryRejected` (409). Between the UPDATE's commit and that read, another actor could delete or re-insert the row. The consequence is bounded: the guarded UPDATE already established that *this* call mutated nothing, so the only observable error is misclassifying a vanished task's 404 as a 409 (or vice versa). No task is ever left in a corrupt or half-reset state. Characterizing it plainly: the transition is atomic; the error-code classification is best-effort. That is the correct trade-off here, since the alternative (a RETURNING clause or a single round-trip returning the pre-image) buys nothing operationally for a local single-writer SQLite deployment.

The reset values line up with the pipeline: `next_retry_at=None` means `fetch_pending_tasks` — whose predicate is `status == PENDING AND (next_retry_at IS NULL OR next_retry_at <= now)` — picks the row up on the very next poll, and `retry_count=0` refreshes the retry budget so the worker's backoff ladder starts clean. The re-queued task flows through the existing worker/rate-limiter/retry machinery with no special-casing. Property tests cover the reset invariant, the non-failed no-mutation guarantee (field-by-field equality before/after), and the idempotence boundary (second retry of a now-pending task is rejected).

### Citation builder purity and the complete/pending invariant

`build_citation` is keyword-only, takes the archive state as explicit arguments, and reads no clock — the rendered date comes from `archived_at.strftime(...)` on the caller-supplied value. There is no import of httpx, sqlalchemy, or any model in the module. This is a genuinely pure, deterministic unit, which is what lets the property tests assert byte-for-byte golden strings.

The invariant is enforced by one guard:

```python
if (archived_url is None) != (archived_at is None):
    raise ValueError("Inconsistent archive state: ...")
```

A half-set pair is an impossible state and it raises rather than guessing. State is then classified solely by `archived_url is None`, and the pending branch structurally cannot carry an `archived_at`. This is the fail-fast posture the project asks for — no fallback paper over a contradictory input.

### Format dispatch and backward compatibility

Formats are resolved through two dict tables keyed by `CitationFormat`, one for complete and one for pending. The markdown formatters are the former `_format_complete` / `_format_pending` bodies verbatim, so the default output is unchanged — the example tests pin the exact former strings. The non-markdown formatters are each small and derive output only from inputs plus `strftime`, so determinism holds across all four. Two details are correct and worth noting because they are easy to get wrong: `plain` contains no `[text](url)` markdown link syntax (asserted via `"](" not in formatted`), and the pending `bibtex`/`apa` renderers never fabricate an `archived_url` — they express progress through `original_url` + `task_id`, which is the honest representation of a not-yet-archived source. The `_bibtex_key` helper reduces URLs to alphanumerics to keep the citation key syntactically valid, shared by both bibtex formatters (DRY).

### API three-way mapping and the archived_at source

`/api/retry` is a thin mapper: `RetryRejected -> 409` with a detail naming the blocking status, `None -> 404`, `ArchiveTask -> 200`. The 409 detail is human-readable and names the current status, which is the right call for an LLM-facing proxy that reads prose.

`/api/cite` mirrors `create_archive` for validation and dedup, then classifies: a cache-hit is treated as COMPLETE only when `existing.status == SUCCESS and existing.result_url` — a pending/processing dedup hit correctly stays a pending citation. The one semantic wrinkle is the archived timestamp:

```python
if existing.status == TaskStatus.SUCCESS and existing.result_url:
    archived_url = existing.result_url
    archived_at = existing.updated_at   # last-mutation time, used as "archived at"
```

`updated_at` carries `onupdate=_utcnow` and `mark_success` sets it explicitly, so immediately after a successful archive `updated_at` is effectively the archive time and the approximation is accurate. The caveat is semantic: `updated_at` is "last modified", and if any later process touched that row the citation's `archived_at` would drift from the true archive moment. There is no dedicated archived-at column and introducing one is a schema change the PR intentionally avoids. The behavior is defensible for v1; the risk is that the field name promises more precision than the source provides. Documenting the approximation (or sourcing the time from the archive result in a later schema-changing release) would close the gap.

Invalid `format` values are rejected before any handler logic runs: `CiteRequest.format` is typed as `CitationFormat`, so a non-enum value is a 422 at validation time — fail-fast, never a silent downgrade to markdown. A test asserts the invalid-format path logs a warning and returns 422.

### MCP handler error posture

`_handle_archive_and_cite` and `_handle_retry_task` reuse the established exception discipline: `ConnectError`/`ConnectTimeout` and the broader `HTTPError`/`ValueError` both collapse to `{"error": "Backend service unavailable"}`, matching the existing `archive_url` handler so the backend-down contract is uniform across tools. Invalid URL and missing `task_id` are rejected locally before any POST, so no task is created on bad input.

Two asymmetries stand out. First, the pending-guidance branch accesses `data['task_id']` directly while the error branch uses `data.get('detail', ...)`. On a well-formed 200 the key is always present, so this does not fail in practice, but the hard access would turn a malformed-but-200 body into a `KeyError` rather than a graceful message — the defensive `.get()` style used elsewhere would be more consistent. Second, the retry tool funnels 404 and 409 into the same `{"error": detail}` envelope; the not-found-vs-not-failed distinction survives only inside the backend's prose string, not as a structured field. For an LLM caller that reads the message this is adequate and the guidance text (call `get_archive_status(task_id)`) correctly steers the pending completion flow.
